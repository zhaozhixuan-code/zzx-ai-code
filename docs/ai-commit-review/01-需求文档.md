# GitHub 提交 AI 审查与飞书通知：需求文档

版本：v0.1（开发前评审稿）  
编写日期：2026-11-18  
配套文档：[开发文档](02-开发跟踪文档.md)  
当前状态：需求与开发方案已整理；尚未接入真实仓库、模型和飞书机器人。

## 1. 目标与背景

用户希望在代码推送到 GitHub 后，自动逐个审查本次推送中的提交。AI 应按用户制定的规则主动查阅相关代码、追踪业务链路、提供有证据的审查结果，并将摘要发送到飞书。

本项目既解决个人代码审查自动化问题，也作为学习 Pi Agent 的实际项目。首版采用 GitHub Actions 触发任务、Python 编排流程、Pi 执行审查、飞书自定义机器人接收通知。

成功的标准不只是“模型返回一段文字”，而是：提交范围准确、源码版本正确、证据可定位、失败可识别、报告可追溯。

## 2. 用户已明确的需求

| 编号 | 需求 |
|---|---|
| U-01 | 监控用户指定的 GitHub 项目，有新的提交后启动审查。 |
| U-02 | 对每个提交按用户制定的要求审查，而不是只处理一次 push 的最后一个提交。 |
| U-03 | AI 能查阅相关代码和调用链，不局限于对 diff 做一次问答。 |
| U-04 | 审查结果发送到飞书。 |
| U-05 | 审查应区分事实、假设与缺失证据，不把潜在路径认定为实际发生过的故障。 |
| U-06 | 本次交付是需求与开发文档，不授权修改现有业务代码或部署线上服务。 |

后续条目为满足上述需求提出的首版设计，配置值可在开发前调整。

## 3. 首版范围

### 3.1 纳入首版

- 单个 GitHub 仓库、明确配置的受信任分支。
- 由 push 事件启动，不采用定时轮询。
- 手动指定提交执行审查，用于调试、补跑和验收。
- 普通提交、根提交、合并提交的明确比较规则。
- 一次 push 多个提交，按拓扑顺序逐个处理；批量任务可分批执行。
- 为每个提交准备对应版本的源码与 diff。
- 按受信任的审查规则进行只读审查。
- 输出结构化报告、可阅读的完整报告和飞书摘要。
- 记录审查与通知状态，提供有限保留期内的去重和补跑能力。
- 处理超时、限流、格式错误、源码缺失及通知失败。

### 3.2 不纳入首版

- 自动修改代码、创建修复提交或自动合并。
- 阻断 push、阻断主分支合并或自动判定上线资格。
- 对整个 GitHub 账号下所有仓库自动安装监听。
- Web 管理后台、用户系统和复杂任务平台。
- 自动访问数据库、生产日志、真实支付或短信等外部业务系统。
- 自动执行待审查仓库中的测试、构建、安装脚本或 Maven。
- 依赖模型给出“99% 置信度”作为验收依据。
- 在无人授权时扫描仓库全部历史。

后续可复用审查内核支持 PR 审查、多仓库 Webhook 服务或人工批准后的验证，但不提前实现。

## 4. 核心使用流程

1. 开发者将一个或多个提交推送到已配置的分支。
2. GitHub Actions 读取 push 事件，确定仓库、分支、before SHA 和 after SHA。
3. 编排程序计算新增提交列表，为每个提交建立审查记录。
4. 程序准备当前提交、父提交的源码快照和差异文件。
5. Pi 根据规则读取差异、搜索相关实现、追踪调用与数据写入流程。
6. 程序校验输出结构及代码引用，保存完整报告和执行状态。
7. 审查批次结束后，飞书收到摘要及 Actions 运行链接。
8. 失败、未完成或通知状态不明的任务可手动补跑；补发通知不重复调用模型。

只存在于开发者本地、尚未 push 到 GitHub 的提交不会触发该流程。

## 5. 功能需求

### F-01 触发与配置

- 支持 `push` 和 `workflow_dispatch`。
- 仓库、分支白名单、模型供应商、模型名称、超时及通知策略可配置。
- 忽略删除分支事件，不审查已删除的分支顶端。
- 首次启用前确认目标分支的历史范围；默认从启用后的 push 开始，不自动补审全部历史。
- 脚本、扩展和审查规则来自固定的受信任控制版本，版本写入报告。

### F-02 提交范围

- 普通 push：审查 after 可达、before 不可达的提交。
- 不直接依赖 Webhook 中可能不完整的 `commits` 数组作为唯一提交来源。
- 对合并提交，以第一父提交为比较基准；合并引入的分支提交仍按本次新增集合各自审查。
- 对根提交，以空树为比较基准。
- 新建分支没有有效 before 时，必须显式采用“指定基线”或“审查截至 after 的可达历史”策略。未配置时标记为需要确定范围，不默默只审查 HEAD。
- 强制推送按 Git 可达性计算，报告中记录此事件。缺少必要 Git 对象时明确失败，不猜测基准。
- 任何批量限制均不能导致提交静默丢失；必须列出已处理与未处理 SHA，并提供分批补跑入口。

### F-03 版本与审查对象

- 审查提交 C 时读取 C 的源码，不能用当前最新源码代替。
- 可查阅父提交源码，以判断缺陷是否由本次改动引入。
- 报告只将本次变化引入或明显恶化的问题列为正式发现。
- 旧问题、无关重构建议和个人风格偏好不混入正式缺陷列表。
- 重命名、删除和二进制变化明确标注；无法解析的变化进入覆盖限制。
- Git 子模块内容、Git LFS 实体及外部依赖源码不默认保证可用，缺失时必须说明对判断的影响。

### F-04 Agent 审查行为

- 从 diff 开始，根据疑点主动读取文件、搜索引用和追踪业务链路。
- 按需核对入口参数、条件分支、服务、仓储、字段来源及创建/更新流程。
- 能区分源码可证明的缺陷与实际运行事故；没有线上数据或日志时不得声称线上已发生。
- 不为了凑数而输出问题，允许没有正式发现。
- 疑点无法证实时，说明缺少的证据；不伪造测试、日志或运行结果。
- 提供受限的读取、搜索和列目录工具；不提供任意 Shell、文件修改或网络业务调用工具。
- 待审查代码、提交说明及仓库内的提示内容均视为输入材料，不得改变受信任的审查规则或发送目标。

### F-05 审查规则

规则集中维护，至少包括：

1. 审查重点：正确性、权限、数据边界、事务、并发、金额和状态变化等；按实际变更选择。
2. 证据要求：文件、版本、行号、触发条件、调用关系、影响。
3. 排除项：纯风格意见、缺少依据的性能猜测、与本次提交无关的问题。
4. 输出格式与严重级别。
5. 执行限制：只读、不执行项目代码、不访问真实业务系统。

审查规则有版本与内容摘要。修改规则后，可对相同提交建立新的审查记录。

### F-06 结构化结果

每份报告必须包含：

- 仓库、分支、完整 commit SHA、父提交 SHA、提交链接。
- 任务 ID、审查键、运行链接、开始及结束时间。
- Pi 版本、模型配置、规则摘要、控制版本、报告协议版本。
- 审查状态、审查结论、摘要、正式发现、待验证事项和覆盖限制。
- 每个正式发现的严重级别、标题、触发条件、变更锚点、相关证据、影响、建议及验证方式。

严重级别：

| 级别 | 含义 |
|---|---|
| P0 | 有充分证据表明会造成严重安全、重大数据破坏等紧急问题。 |
| P1 | 在明确条件下会导致核心功能错误、重要权限或数据完整性问题。 |
| P2 | 有明确影响、值得修复的一般功能缺陷。 |

级别不等于发生概率。首版不自动以级别阻断业务代码交付。

### F-07 状态与结论

| 字段 | 取值 | 说明 |
|---|---|---|
| 审查状态 | `completed` | 按既定范围完成本次审查，仍可能存在已披露的静态分析限制。 |
| 审查状态 | `incomplete` | 关键文件未读取、资源耗尽或部分范围未覆盖。 |
| 审查状态 | `failed` | 模型不可用、输出无效或准备阶段失败，未形成有效审查。 |
| 审查状态 | `skipped` | 删除分支等不适用事件，或明确命中可复用结果。 |
| 审查结论 | `issues_found` | 至少有一个满足证据要求的正式发现。 |
| 审查结论 | `no_findings` | 审查完成，本次未发现有充分证据的问题。 |
| 审查结论 | `inconclusive` | 未能形成完整结论。 |

`no_findings` 不表示代码绝对正确或通过线上验证。失败、超时和空输出不能转换成 `no_findings`。

未完成的审查即使已发现有效问题，整体结论仍为 `inconclusive`，但必须保留这些问题并在通知中显示；不能因为整体未完成就丢弃已确认的发现。复用旧报告时保留原报告的完成状态，另在执行记录中标注 `reused`，不将旧报告改写成 `skipped`。

### F-08 飞书通知

- 默认每个执行批次汇总一条摘要，而不是每次工具调用都发消息。
- 摘要包含仓库、分支、每个提交的状态、问题数量、重点发现及完整报告入口。
- 多个批次属于同一 push 时，消息标注批次号；手动补跑明确标注。
- 即使没有发现问题，也发送一次完成通知；可通过配置改为仅问题或失败通知。
- 消息过长时截断展示并标注“其余见完整报告”，不能截断实际保存的报告。
- GitHub 私有仓库的完整报告链接需要接收者有对应权限。
- 飞书地址和签名密钥只对通知步骤可见，不传入 Agent 子进程。
- 同时检查 HTTP 状态和飞书响应中的业务成功码。
- 发送结果不明确时标记 `unknown`，人工确认后补发，避免盲目重试产生重复消息。

### F-09 存储、去重和补跑

- 保存机器可读 JSON、完整 Markdown 和批次清单。
- 首版使用 GitHub Actions artifacts，建议保留 30 天；实际以仓库和平台允许值为准。
- 可在保留期内查找相同审查键的成功结果并复用；查询失败不能当作未审查而静默继续。
- artifact 不是永久数据库，不能承诺保留期外去重或严格并发幂等。
- 相同审查键并发运行时，首版可能重复审查或通知；报告和通知携带相同键以便识别。
- 支持仅补发通知、重试失败审查、强制重新审查和历史范围分批补审。
- Webhook 不提供端到端事务时，不承诺消息严格恰好发送一次。

## 6. 非功能要求与建议默认值

以下为建议初值，需在真实仓库试跑后调整，不能描述成已验证能力。

| 项目 | 建议值或要求 |
|---|---|
| 单提交审查超时 | 8 分钟，超时明确记录。 |
| 单批提交数 | 10 个，批内顺序执行。 |
| 同次 push 批次并行度 | 2；不因此丢弃较早的 push。 |
| 自动处理提交数上限 | 每次 push 50 个；超限明确待分批处理，不静默截断。 |
| 单文件读取上限 | 可配置，返回截断标记，关键证据受影响时判定未完成。 |
| 内容过滤 | 不向模型开放密钥文件、私钥等受限路径；过滤配置可维护。 |
| 成本控制 | 固定模型、超时、读取限额与最大重试；记录可获得的用量，不能把超时等同于精确金额上限。 |
| 可追溯性 | 每个发现可定位到 commit 和实际源码位置。 |
| 输出时间 | 存储用 UTC，用户可见时间标明时区，默认 Asia/Shanghai。 |
| 凭据 | GitHub Secrets 管理，不写报告、不写调试日志。 |

## 7. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A-01 | 普通单提交 push | 自动触发、SHA 正确、报告落盘、飞书收到摘要。 |
| A-02 | 一次 push 三个提交 | 三个提交均有记录；各自读取对应版本源码。 |
| A-03 | 早期提交有缺陷、后续提交修复 | 前者和后者使用不同快照，不拿修复后的代码替早期提交下结论。 |
| A-04 | 已知缺陷样例 | 找到预设缺陷，给出正确触发条件及可定位证据。 |
| A-05 | 上游已有校验的反例 | 不将已被上游校验排除的路径报告为正式缺陷。 |
| A-06 | 根提交、合并、重命名、删除 | 比较语义及引用版本正确；无法覆盖部分有明确说明。 |
| A-07 | 模型超时或输出无效 | 状态为失败或未完成，不能通知“审查通过”。 |
| A-08 | 受限路径、越界路径、恶意仓库指令 | 工具拒绝读取越界或受限内容，不执行仓库指令、不修改文件。 |
| A-09 | 飞书返回业务错误 | 标记通知失败，报告仍保留，可只补发通知。 |
| A-10 | 飞书接收成功但客户端超时 | 标记结果不明，不自动重复发送。 |
| A-11 | 重跑相同提交 | 保留期内能识别匹配结果；强制重跑有独立尝试记录。 |
| A-12 | 新分支、强制推送、缺失 Git 对象 | 范围明确或显式报错，不猜测、不漏报覆盖状态。 |
| A-13 | 超出批量上限 | 明确列出未处理提交或待处理范围，支持补跑。 |
| A-14 | 连续快速 push | 每次事件均保留执行记录，不因并发组替换待运行任务而丢失。 |

AI 质量验收使用已标注的真实或构造案例，不用一次正常提交的成功代替全部验收。首次试点应记录漏报、误报和人工复核意见，暂不预设未经测量的准确率承诺。

## 8. 交付物

1. 可维护的审查规则与配置示例。
2. Python 审查编排程序及飞书通知程序。
3. Pi 受限只读工具扩展。
4. GitHub Actions 工作流和 Secrets 配置说明。
5. JSON 报告协议、Markdown 模板及飞书模板。
6. 有明确结果的测试、试跑记录及已知限制。
7. 安装、首次启用、补跑、通知补发和故障排查说明。

## 9. 开发前待配置项

| 项目 | 影响 |
|---|---|
| 目标仓库地址和可访问方式 | 拉取代码、建立链接、配置 Actions。 |
| 需要监听的分支 | 自动触发范围及可信来源。 |
| Pi 使用的模型供应商和具体模型 | 凭据名称、能力、用量与成本。 |
| 飞书群机器人是否创建、是否启用签名 | 通知接入方式。 |
| 用户补充的业务审查重点 | REVIEW.md 的业务规则。 |
| 是否需要首次补审历史 | 首次基线、历史批量范围。 |
| 内容过滤、报告保留期及预算偏好 | 可读取范围、存储和运行限制。 |

这些配置缺失不妨碍先开发本地样例与模拟测试，但在完成配置前不能宣称真实链路已经打通。密钥直接配置到 GitHub Secrets，不通过文档或聊天收集。
