# LangChain4j 到 Spring AI Alibaba 迁移实施方案

## 1. 改造目标

将单体应用的主业务 AI 能力从 LangChain4j 迁移到 Spring AI 体系，并使用 OpenAI 兼容接口连接模型。更换兼容服务商时，目标是通过配置修改 endpoint、密钥、模型 ID 和必要的接口路径，不在业务代码中绑定 DeepSeek 或其他厂商 SDK。

本阶段是行为等价迁移，不新增版本管理、回滚、协作编辑或新的生成工作流。LangChain4j 和 LangGraph4j 的现有源码、依赖和学习实现全部保留；日常应用生成改走新的 Spring AI 实现，LangGraph 的 `/workflow/*` 演示 HTTP 映射注释停用。不会把学习用工作流接入应用生成主链路。

建议题目：

> 基于 Spring AI Alibaba 与 OpenAI 兼容模型接口的智能应用生成平台设计与实现

## 2. 当前主链路

```text
AppController
  -> AppServiceImpl.chatToGenCode
  -> AiCodeGeneratorFacade
  -> AiCodeGeneratorServiceFactory / LangChain4j AiServices
  -> 模型流、工具调用、代码解析和保存
  -> StreamHandlerExecutor
  -> SSE 前端、预览和部署
```

迁移时保留应用权限、对话记录、代码生成类型、文件落盘、Vue 构建、预览和部署逻辑，替换模型调用与模型相关适配层。

现有需迁移的行为：

- HTML 和多文件模式：文本流式生成，结束后解析并保存。
- Vue 模式：流式 AI 文本、文件工具调用及其请求/执行事件、生成后构建。
- 创建应用时的代码生成类型路由。
- 按 `appId` 隔离的多轮上下文；MySQL `chat_history` 是用户可见历史，Redis ChatMemory 用于模型上下文。
- 输入安全校验、结构化结果解析和模型监控指标。

## 3. 依赖与版本基线

仓库当前为 Java 21、Spring Boot 3.5.7。官方 Spring AI Alibaba `1.1.2.2` 系列的项目基线为 Spring Boot 3.5.8、Spring AI 1.1.2。先在迁移分支保持当前 Boot 版本加入依赖并做 Maven 解析；若发生版本冲突，再将 `pom.xml` parent 对齐至 3.5.8 后复验。不要只添加一个无效的 Boot 版本属性。

主业务的 OpenAI 兼容模型采用 Spring AI OpenAI Starter。Alibaba Agent Framework 用于 Vue 工具代理迁移。由于此次保留全部 LangChain4j 代码与依赖，不以依赖清理或源码隔离作为本次目标。DashScope Starter 不是当前 OpenAI 兼容主链路所必需。

推荐依赖基线：

```xml
<properties>
    <java.version>21</java.version>
    <spring-ai-alibaba.version>1.1.2.2</spring-ai-alibaba.version>
    <spring-ai.version>1.1.2</spring-ai.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>${spring-ai.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>com.alibaba.cloud.ai</groupId>
            <artifactId>spring-ai-alibaba-bom</artifactId>
            <version>${spring-ai-alibaba.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-starter-model-openai</artifactId>
    </dependency>
    <!-- Vue 模式采用 Spring AI Alibaba ReactAgent 时启用。 -->
    <dependency>
        <groupId>com.alibaba.cloud.ai</groupId>
        <artifactId>spring-ai-alibaba-agent-framework</artifactId>
    </dependency>
</dependencies>
```

两个 BOM 分别管理 Spring AI 和 Alibaba Agent 版本。现有 LangChain4j/LangGraph4j 依赖保留在 `pom.xml`；本阶段只增加依赖，不做排除或清理。所有 Spring AI 组件统一使用 1.1.x，不混用 1.0.x 和 2.x。

### OpenAI 兼容模型配置草案

```yaml
spring:
  ai:
    openai:
      base-url: ${AI_BASE_URL}
      api-key: ${AI_API_KEY}
      chat:
        completions-path: ${AI_COMPLETIONS_PATH:/v1/chat/completions}
        options:
          model: ${AI_MODEL}
          temperature: ${AI_TEMPERATURE:0.7}
          max-tokens: ${AI_MAX_TOKENS:8192}
```

切换服务商时一般修改 `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`；服务商路径不同则同时配置 `AI_COMPLETIONS_PATH`。若路由、Vue 生成和普通生成要使用不同模型，配置中应分别定义模型角色；模型 endpoint/key/model ID 等仍从外部属性读取。OpenAI 兼容不保证工具调用、usage、推理扩展参数和 SSE 格式完全一致，每个目标服务商都需验证。

## 4. 目标结构

```text
AppController / AppServiceImpl
  -> 项目内 AiCodeGenerator 接口（只暴露项目 DTO 和 Flux）
  -> Spring AI 实现
       -> OpenAI 兼容 ChatModel / ChatClient
       -> OpenAI 兼容流式响应
       -> ToolCallback；Vue Agent 视验证结果采用 ReactAgent
       -> ChatMemory 或从 MySQL 历史构造请求上下文
  -> 旧 LangChain4j 服务与 LangGraph4j 学习代码（保留，不接入主生成调用）
  -> 项目内流事件 DTO
  -> 现有代码解析、保存、构建和 StreamHandler
```

不要让 Spring AI 的 `ChatResponse`、`ToolCall` 等类型直接穿透到 Controller、前端协议或业务存储层。项目内适配接口应以 `String`、现有结果 DTO、`Flux` 和流消息 DTO 为边界，方便未来换兼容模型而不改业务服务。

## 5. 分阶段实施

### 阶段 A：依赖和最小模型原型

1. 在独立迁移分支开始，记录当前工作区状态并保护既有改动。
2. 按第 3 节增加 BOM/OpenAI Starter，确定 Boot 兼容版本；先执行 Maven 依赖解析和编译。
3. 用配置提供的 OpenAI-compatible endpoint 做一次同步调用和文本流调用，不把密钥提交到仓库。
4. 验证默认 completions 路径、自定义 headers、超时、max tokens、流式断开及错误映射。

阶段验收：依赖可解析、后端可编译启动、模型和配置均可通过属性切换；记录所用 endpoint 协议要求。

### 阶段 B：普通生成与路由

1. 新建项目内 Spring AI 生成服务，实现 HTML、多文件同步/流式调用。
2. 把系统提示词文件接入 Spring AI Prompt/ChatClient；保留提示词内容和角色。
3. 将输出转换到现有 `HtmlCodeResult`、`MultiFileCodeResult`，完成必要字段校验。
4. 迁移代码类型路由，返回现有 `CodeGenTypeEnum`，定义模型返回空值、非法值时的确定性处理。
5. 接入现有 `AiCodeGeneratorFacade`；保留代码解析器、文件保存器和 `Flux<String>` 上下游契约。

阶段验收：HTML 与多文件通过现有入口完成生成、解析、保存和预览；流结束/异常不混淆。

### 阶段 C：Vue 工具代理和流事件

1. 先写小型原型验证 OpenAI 兼容模型的流式工具调用：工具名称、参数片段、工具执行和模型续答。
2. 将文件读取、目录读取、写入、修改、删除和 exit 工具逐项适配为 Spring AI `ToolCallback` 或 Alibaba Agent 工具。
3. 通过服务端上下文传入 `appId`，不要让模型决定应用 ID；保持工具只能操作原有项目目录范围。
4. 转换为现有 `AI_RESPONSE`、`TOOL_REQUEST`、`TOOL_EXECUTED` 内部消息 DTO，检查前端 `JsonMessageStreamHandler` 的假设。
5. 仅当默认 Spring AI 流不能呈现既有事件时，增加适配循环或调整前端事件协议；改动保持最小并同步测前后端。
6. Vue 生成完成后保留当前构建与保存时序。

阶段验收：至少完整验证读取、写入、修改和最终续答；删除受保护文件、工具异常、非法参数、模型中断都有明确结果。

### 阶段 D：对话上下文

1. 将框架消息转换从 `ChatHistoryService` 中抽离，消除其对 `MessageWindowChatMemory` 的直接依赖。
2. 明确 MySQL 历史和模型上下文边界：查询同一 `appId` 最近消息、按时间升序组装、限制条数与 token/窗口策略。
3. 评估是否继续用 Redis。若保留，使用 Spring AI 支持的 ChatMemory Repository/Advisor，或实现项目自己的 Repository；避免同时从 Redis 和 MySQL 重复追加历史。
4. 验证 assistant、user、assistant tool call、tool result 消息序列在下一轮可被模型接受。若无法持久化工具调用消息，记录并落实兼容处理。
5. 验证应用 A/B 上下文隔离、缓存过期及历史回填。

阶段验收：同一应用多轮上下文可用，应用间不串话，历史消息没有重复或顺序颠倒。

### 阶段 E：校验、监控和旧接口停用

1. 将输入安全检查改为框架无关校验或 Spring AI Advisor；保持现有阈值和拒绝语义。
2. 用 Spring AI Observation/Micrometer 替换 LangChain4j Listener；保留模型、用户、应用、成功失败、耗时和 token 指标。缺失的 usage 不填假值。
3. 保留原 LangChain4j 服务、模型配置、Memory、工具、Guardrail、监控实现及 `dev.langchain4j` 定制源码，不让新的应用生成入口调用它们。
4. 在 `WorkflowSseController` 中注释 `/workflow/execute`、`/workflow/execute-flux`、`/workflow/execute-sse` 的映射注解，保留 Controller 方法和 Graph 实现源码供学习。
5. 应用的 `/app/chat/gen/code` 路径保留，由 `AppServiceImpl` 切换到新的 Spring AI 实现；不是停用日常生成 API。

阶段验收：默认应用主链路使用 Spring AI；LangGraph 演示接口无法从 HTTP 访问；旧源码与依赖仍保留且可编译。

## 6. 代码改动范围清单

重点后端位置：

- `pom.xml`：加入 Spring AI 与 Spring AI Alibaba BOM、OpenAI Starter、Agent Framework；保留全部 LangChain4j/LangGraph4j 依赖。
- `src/main/resources/application.yml`：改为 OpenAI 兼容服务配置，并允许从环境属性覆盖。
- 新增独立的 Spring AI 生成服务与 OpenAI-compatible 模型配置，不覆盖旧 `AiCodeGeneratorService` 和 `AiCodeGeneratorServiceFactory`。
- `src/main/java/com/zzx/zzxaicode/service/impl/AppServiceImpl.java`：将主应用生成和创建时路由改为注入新的 Spring AI 服务。
- 新增 Spring AI 路由器，保留 LangGraph 学习代码使用的旧 `AiCodeGenTypeRoutingService*`。
- 新增 Spring AI 工具适配器委托现有文件工具业务方法，避免改写旧 LangChain4j 工具源码。
- `src/main/java/com/zzx/zzxaicode/core/AiCodeGeneratorFacade.java`：切换到 Spring AI 服务并保留项目 SSE DTO、代码解析和保存边界。
- 新增 Spring AI 历史上下文适配，不改写旧 ChatMemory 方法和 LangChain4j 接口。
- 新增 Spring AI 监控适配；原 LangChain4j Listener、Guardrail、配置类和 DTO 保留供旧代码使用。
- `src/main/java/com/zzx/zzxaicode/controller/WorkflowSseController.java`：注释停用 workflow 映射，保留控制器方法和调用的学习源码。
- `zzx-ai-code-frontend/src/pages/app/AppChatPage.vue` 和现有 stream handlers：只有事件格式确实无法保持时才修改。

## 7. 验证清单

### 功能回归

| 模式/条件 | 必验行为 |
|---|---|
| HTML | 流式片段、正常结束、解析、保存、预览 |
| 多文件 | JSON/结构化转换、字段缺失处理、保存文件内容 |
| Vue 工具模式 | 工具请求/执行事件、工具参数、工具结果、模型续答和构建 |
| 模型路由 | 三种支持类型、非法和空结果 |
| 多轮对话 | appId 隔离、消息排序、窗口长度、工具消息处理 |
| 异常路径 | 401/429、超时、断流、工具失败、解析失败不显示成功 |
| 权限路径 | 现有未登录、跨用户请求保持拒绝 |
| 模型切换 | 仅改配置即可连接至少两个 OpenAI 兼容端点；分别记录差异 |

### 对比指标

- 首 token 延迟、总生成耗时、请求成功率、内容可解析率、Vue 工具调用完成率、Vue 构建通过率、token usage 可获取比例。
- 固定提示词、模型 ID、temperature、max token 和网络环境；每个用例多次执行，报告样本量和 provider 能力差异。
- 外部模型随机性和服务端限流作为实验条件记录，不能将一次生成质量差异直接归因于框架。

## 8. 开工顺序与当日目标

建议下午按以下顺序推进：

1. 建迁移分支/提交基线，确认 JDK 21 实际生效。
2. 加 Spring AI 与 Alibaba BOM、OpenAI Starter 和 Agent Framework；保留旧依赖，先让 Java 21 下依赖解析、编译通过。
3. 配一个 OpenAI-compatible endpoint，只验证纯文本调用和 Flux 流。
4. 迁移 HTML 模式并通过原有 `/app/chat/gen/code` 完成保存和预览。
5. 再决定 Vue Agent Framework 的接入方式；不要在尚未验证工具流协议前删除旧服务。

当天的合理交付是“依赖与配置确定 + HTML 迁移跑通 + Vue 工具流原型结论”，而不是宣称完整迁移完成。模型密钥需通过本地安全配置或环境变量提供；文档和 Git 中不写入密钥。

## 9. 风险与控制

- **Spring Boot / Spring AI 版本冲突**：按官方 BOM 管理，先在 JDK 21 下构建；不要直接依赖最新主版本号。
- **OpenAI 兼容不等于完全一致**：endpoint、path、SSE、工具调用和厂商扩展参数逐项验证；业务代码只使用通用 API，个别差异通过 provider 配置处理。
- **工具事件聚合差异**：模型流式返回可能将工具请求聚合为完整调用后才执行，未必与现有 TokenStream 的 partial request 一致；以当前前端实际依赖的事件为验收依据。
- **ChatMemory 语义变化**：要同时对齐应用隔离、消息窗口、Redis TTL、MySQL 回填和工具调用历史。
- **旧代码与新框架共存**：保留旧依赖时注意新旧 Bean、类型和配置名称不冲突；主业务注入新适配类，旧接口不在主链路调用。workflow HTTP 映射需明确停用。
- **避免范围膨胀**：本次只替换 AI 框架接入和必要适配，不顺带重做业务功能、数据库和界面。

## 10. 完成定义

主业务迁移完成需同时满足：

1. 三种代码生成类型仍从原应用入口工作。
2. OpenAI 兼容模型连接信息可通过配置切换，业务层没有 DeepSeek 专属调用。
3. 工具流、对话上下文、代码保存、构建、预览和部署完成针对性回归。
4. 应用主业务入口调用 Spring AI；原 LangChain4j 和 LangGraph4j 源码及依赖保留；`/workflow/*` 映射已注释停用。
5. 只报告实际完成的构建、测试和真实模型验证，不把配置完成等同于端到端通过。

本方案不包含版本管理、回滚、额外质量工作流或线上部署迁移，也不要求删除或隔离 LangChain4j/LangGraph4j 学习代码。
